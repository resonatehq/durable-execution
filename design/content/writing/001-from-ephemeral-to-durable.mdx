Here is an agent. It calls a model, runs whatever tools the model asks for,
feeds the results back, and repeats until the model stops asking.

```python name="agent"
async def agent(prompt: str):
    messages = [{"role": "user", "content": prompt}]
    response = await llm(messages)
    messages.append(response)

    while "tool" in response:
        name, args = response["tool"]
        result = await tools[name](**args)
        messages.append({"role": "tool", "content": result})

        response = await llm(messages)
        messages.append(response)

    return response["content"]
```

That is the whole program, and a good one. The program is also ephemeral,
alive only as long as the process running it. `messages`, the loop position,
the half-finished tool call — all of that lives in one process's memory. Kill
the process and the whole lot is gone.

Here is that program on the stack. Two calls, one frame each, pushed and
popped by `agent` and nothing underneath them:

For a function that runs in ten milliseconds, nobody cares. This one runs for
minutes. It makes twenty model calls and a dozen tool calls, and over those
minutes a deploy happens, a spot instance is reclaimed, an OOM killer picks a
victim. When that happens you start over from the first token: every model call
paid for twice, every tool call run twice. Nineteen successful steps are not
recoverable, because nothing wrote them down.

Notice what that program already is, though: nothing in the code mentions
crashing. Interruption-agnostic code, buying interruption-intolerant
execution. Hold on to both halves of that — the rest of this post is an
argument about which half you are allowed to keep.

## Where this sits

Running a durable function splits in two, and both halves are worth naming
before starting, because only one of them is the subject here.

`execute_until_blocked_outer` deals with the world outside the function. The
outer half takes a task off a queue, claims the task so that no one else picks
up the same work, runs the function, and then completes or reschedules the
task depending on how that went:

```python name="execute_until_blocked_outer"
async def execute_until_blocked_outer(queue, store):
    task = await queue.claim()
    if task is None:
        return

    await execute_until_blocked_inner(store, task)
    await queue.complete(task)
```

That is nearly the whole of the outer half. The half is short, and the parts
that are hard — what a claim means when the claimant dies, how long a claim
lasts — are properties of the queue, not of this function.

`execute_until_blocked_inner` is the part that runs your code: start the
function, or restart it, and carry it forward until it finishes or reaches
something it cannot make progress on by itself. Everything from here on is
inside that call.

The name promises blocking, and nothing in this post blocks. The agent's calls
all complete in the same process, so the inner half always runs the function to
the end. Blocking shows up when a call is settled by someone else — a remote
call, a timer, a human — and that is a later post. The machinery below is what
makes it possible.

## Interruption-aware code

So you write them down. Before touching the agent, decide what you are writing.

### The store

A step has an identity, the arguments it was called with, and either an outcome
or not one yet. That is a promise:

```python name="Promise"
PENDING, RESOLVED, REJECTED = "pending", "resolved", "rejected"


@dataclass(frozen=True)
class Promise:
    id: str
    state: str = PENDING
    param: Any = None
    value: Any = None
```

And a store holds them:

```python name="Store"
class Store:
    def __init__(self):
        self._db: dict[str, Promise] = {}

    def create(self, id: str, param: Any) -> Promise:
        return self._db.setdefault(id, Promise(id, param=param))

    def settle(self, id: str, state: str, value: Any) -> Promise:
        p = self._db[id]
        if p.state == PENDING:
            self._db[id] = Promise(id, state, p.param, value)
        return self._db[id]
```

This one is a dict, so the store dies with the process and is useless for the
actual job. Ignore that for now — a real store is a database, and swapping one
for the other changes nothing above this line. What matters is the interface —
two operations — and three properties of that interface.

The param is on the promise so that a process which did not make the call can
still make it — an id on its own does not say what to run.

All three properties show up in one session, which is the whole specification:

```python name="Store, in one session"
#                                 Promise(id, state, param, value)

s = Store()

s.create("a", 1)                # Promise("a", PENDING, 1)
s.create("a", 2)                # Promise("a", PENDING, 1)      <- 2 discarded

s.settle("a", RESOLVED, 9)      # Promise("a", RESOLVED, 1, 9)
s.settle("a", RESOLVED, 8)      # Promise("a", RESOLVED, 1, 9)  <- 8 discarded
s.settle("a", REJECTED, Err())  # Promise("a", RESOLVED, 1, 9)  <- so is Err

s.create("a", 3)                # Promise("a", RESOLVED, 1, 9)  <- replay sees
```

Nothing after the first create changes the param, and nothing after the first
settle changes the outcome. Read down the right-hand column and the three
properties name themselves.

**`create` is idempotent.** Call `create` once or a thousand times with the
same id and you get the same promise, whatever param you pass after the first
— the first one is of record too. This is what makes replay work: a restarted
program calls `create` on ids that already exist and gets back what happened
last time.

**Settling is first-writer-wins.** `settle` moves a pending promise to
`RESOLVED` or `REJECTED`, and refuses to move a settled one anywhere. A step
that runs twice cannot produce two different outcomes of record.

**Settling returns the promise, and it is not necessarily yours.** This is the
one that is easy to skip. `settle` returns whatever is in the store *after* the
write — which, if someone beat you to it, is their outcome and not the one you
just passed in. So the rule at every call site is: settle, then read what came
back, then return or raise from that. Never from your local result.

Skipping the read-back looks harmless until two workers run the same step.
Worker A calls the model and gets a response. Worker B calls the model and the
request times out. Both settle the promise; the store keeps whichever landed
first, say A's value. If B raises its own timeout instead of reading back, the
two workers now disagree about what that step did, and carry that disagreement
forward into two different message histories for the same run.

<PullQuote>The promise is the record. If you do not read it, you are not using it.</PullQuote>

The same rule covers restarts, not just races. On replay the promise may already
be rejected from the first run. You raise the stored error. You do not call the
model again to find out.

<Details summary="The three properties, as tests">

`ids` and `values` are Hypothesis strategies — any identifier, any outcome. Each
property runs over a few hundred generated triples, so these are claims about
every id and every pair of outcomes, not about the one session above.

```python name="properties"
@given(ids, values, values)
def test_create_is_idempotent(id, a, b):
    s = Store()
    assert s.create(id, a) == s.create(id, b)

@given(ids, values, values)
def test_first_settle_wins(id, a, b):
    s = Store(); s.create(id, a)
    assert s.settle(id, RESOLVED, a) == s.settle(id, RESOLVED, b)

@given(ids, values, values)
def test_settled_stays_settled(id, a, b):
    s = Store(); s.create(id, a); s.settle(id, RESOLVED, a)
    assert s.create(id, b).value == a == s.settle(id, REJECTED, b).value
```

The third chains a `create` and a `settle` through one assert, so both halves of
*settled stays settled* land in a single line: a later create sees the settled
value, and a later settle cannot move it.

What the card leaves out is the import and the two strategy definitions. They
are three more lines of setup on a block that is here to be read rather than
run.

</Details>

Everything else in a durable execution engine is a policy on top of these
three properties. That is the claim of this post, and worth being suspicious
of, so watch how far the claim goes.

### Wrapping by hand

Now put the store in the agent. Every call site gets the same treatment: build
an id, create the promise, do the work if it is still pending, settle it either
way, then return or raise based on what the store says.

```python name="agent, wrapped by hand"
async def agent(prompt: str, store: Store, run_id: str):
    messages = [{"role": "user", "content": prompt}]

    # ---- bookkeeping -------------------------------------------------
    step = 1
    id = f"{run_id}.{step}"

    p = store.create(id, messages)
    if p.state == PENDING:
        try:
            result = await llm(store, id, messages)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == REJECTED:
        raise p.value
    response = p.value
    # ------------------------------------------------------------------

    messages.append(response)

    while "tool" in response:
        name, args = response["tool"]

        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}.{step}"

        p = store.create(id, response["tool"])
        if p.state == PENDING:
            try:
                result = await tools[name](store, id, **args)
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == REJECTED:
            raise p.value
        result = p.value
        # --------------------------------------------------------------

        messages.append({"role": "tool", "content": result})

        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}.{step}"

        p = store.create(id, messages)
        if p.state == PENDING:
            try:
                result = await llm(store, id, messages)
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == REJECTED:
            raise p.value
        response = p.value
        # --------------------------------------------------------------

        messages.append(response)

    return response["content"]
```

This works. Most teams end up here, and the code is correct as written.
Nothing is wrong with the approach except the cost.

Three things happen, in that order, and all three happen in `agent`'s own
frame. The bookkeeping is not underneath the business logic but interleaved
with it. That is not a metaphor for the maintenance problem. That is the
maintenance problem: there is no layer to fix, only call sites.

Note the `p =` on both settle branches. That assignment is the whole third
property. Write `store.settle(id, RESOLVED, value)` without the assignment and
the code still runs, still passes tests, and quietly returns local outcomes
the store disagrees with. The failure comes only when two workers overlap,
which is exactly the case the store exists for.

The obvious cost is that fourteen lines of agent became sixty-four. Everything
between the rules is bookkeeping; what is left outside them is the program you
meant to write — eight lines of it, with its three calls swallowed by the
blocks. Three call sites, three copies of the same block.

This is interruption-aware code: the program is now written in terms of the
interruptions the program has to survive. The trade does buy
interruption-tolerant execution, which is what you wanted. The awareness is
the price, and the price is charged at every call site.

The duplication part is easy to fix — factor it out:

```python name="durable"
async def durable(store, id, func, *args):
    p = store.create(id, args)
    if p.state == PENDING:
        try:
            result = await func(store, id, *args)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == REJECTED:
        raise p.value
    return p.value
```

Which turns every call site into one line:

```python name="call site"
response = await durable(store, f"{run_id}.{step}", llm, messages)
```

Good. The duplication is gone, and the read-back is now written once instead
of at every call site. The helper also changes the picture above: create,
call, and settle now happen in `durable`'s frame, one level below `agent`.
Hold on to that; that is where this is going.

Three things are not gone.

**The store and the id are part of the signature.** `agent` needs a `store`
and a `run_id` to be durable, so every caller needs them — and so does
everything `agent` calls, which is why `llm` and the tools now take them too,
and why they must pass them on again to anything they call. The id handed down
is the parent of the ids that come back: step `run1.2` creates `run1.2.1`
beneath. That is how durability composes, and also how durability leaks:
upward through the type of every function that participates.

**The id is a counter, and the counter has to be right.** In a straight line of
code you can name your steps `"plan"`, `"search"`, `"report"`. In a loop there
is no fixed set of steps, so identity falls back on position — and position has
to land on the same number for the same call on every replay. That means the
replayed program has to take the same path through the loop. Recovery is only
correct if the function is deterministic between recorded steps, and nothing in
the code says so. Add an `if` on a timestamp, iterate a set, skip a tool call
when a flag is set, and the counter drifts. Step 7 on the replay is not step 7
from the first run, and the agent resumes with someone else's answer. No test
catches this; it shows up as an agent that occasionally continues a conversation
it never had.

**A step can still run twice.** Between `llm(messages)` returning and the
settle committing, the process can die. The call happened, the record did not,
and on restart you make the call again. You can shrink that window but you
cannot close the window, so the honest position is that steps execute at least
once, and anything with an external effect has to tolerate that.
First-writer-wins plus reading back is what keeps at-least-once from turning
into disagreement.

The third one is a property of the problem, not of this approach — it does not
change in the next section. The first two do.

## Interruption-agnostic code

Look at what `durable` actually does: takes an identity, checks whether an
outcome is known, produces one if not, records the outcome, and reports
whatever the store ended up holding. Nothing in the helper mentions agents,
models, or tools. No version of the helper would be specific to this program —
the shape is the same for every call in every durable function anyone will
ever write.

The best solution is to stop threading that by hand and make it the primitive.
Persist promises, and let the call sites use them.

```python name="agent"
@resonate
async def agent(prompt: str):
    messages = [{"role": "user", "content": prompt}]
    response = await llm(messages)
    messages.append(response)

    while "tool" in response:
        name, args = response["tool"]
        result = await tools[name](**args)
        messages.append({"role": "tool", "content": result})

        response = await llm(messages)
        messages.append(response)

    return response["content"]
```

Same program as the top of this post. The bookkeeping did not move into a
helper; the bookkeeping moved under the language. `await llm(messages)`
derives an id, creates the promise, runs the call if the promise is pending,
settles the promise, reads back what the store holds, and returns or raises
from that. A crash and restart replays the function, finds the promises that
survived, and skips past the work they represent.

Interruption-agnostic code, interruption-tolerant execution. Nothing about the
guarantee changed between this section and the last one — what moved is where
the awareness lives. It went out of your program and into the runtime.

The call site no longer calls `llm` but `invoke`, and `invoke` is the
runtime's frame — deriving the id, creating the promise, calling the real
function, and settling the promise with whatever came back. The frames above
`invoke` are always these three, in this order, whatever the call underneath
happens to be. That is the manual diagram with one frame slid underneath, the
same frame `durable` pushed, except you no longer pass a store or an id and no
longer have to remember to call the thing at all.

Step 2 is the interesting one on a restart. `invoke` derives the same id, finds
the promise already settled from a previous life of this program, and returns
its value without ever reaching step 5. The model is not called again.

Every frame in that picture disappears when the process dies. The promise
created in step 3 does not. That is the entire trick: the stack is ephemeral, so
put the record somewhere the stack is not.

The store is gone from the signature — the decorator supplies the store. The
counter is gone too. The counter still exists, maintained by code whose only
job is maintaining it, so the same id is computed on every replay rather than
depending on you not having written an `if` in the wrong place. And the `p =`
you have to remember thirty times is written once, in the runtime, where
forgetting is a bug someone else already found.

## Why promises

A promise is the right primitive because it is already the unit that both the
language and the network agree on.

The language agrees: `await` is how a Python program says *block until this
value is known*. Nothing about that requires the value to be produced in this
process, or within this process's lifetime. Point `await` at a persisted promise
and the same syntax means block until this value is known, wherever and whenever
it becomes known. `raise` comes along for free — a rejected promise is an
exception that survived a restart.

The network agrees: a remote call is a promise held by someone else. The caller
does not need to know which process settles it, or whether that process is the
one that started the work. It waits on an id.

From there the rest falls out. Recovery is reading ids you already have. Fan-out
is many ids. A timeout is a promise settled by a clock instead of a function. A
retry is a policy on an unsettled promise. Concurrency across machines is a
promise whose children are also promises.

None of that needs a workflow DSL, a state machine, or a YAML file describing
your control flow. The control flow is the Python. The durability is the store.

## What that leaves

The idea is small. The engineering is not, and that is where the rest of this
project goes:

- **A real store.** `create` and `settle` have to keep those three properties
  under concurrent writers, across processes, across regions — which a dict does
  not. In particular, settle-and-return-the-winner has to be one atomic
  operation, not a read followed by a write.
- **The scheduler and the queue.** Something must decide which pending promises
  are being worked on and by whom, and hand them to the outer half as tasks.
- **Leases and failure detection.** A worker that dies mid-call has to be
  noticed and its work reassigned, without two workers running the same step in
  parallel more often than necessary.
- **At-least-once, and living with it.** The window is still there. It gets
  handled once, in one place, instead of at every call site.

That is roughly five thousand lines. The next post is about the calls this
process does not make itself.
