An agent that runs for minutes has a problem a ten-millisecond function never
has: the process can die halfway through, and everything the agent did dies
with it. This post fixes that with one primitive, a persisted promise per
function call. First by hand, so you can see what the fix costs, then with a
decorator.

Listing 1 shows a simple tool-calling agent. First the function prompts a
model. If the model returns a tool call, the function invokes the tool and
prompts the model again. When the model returns an answer instead of a tool
call, the function returns the answer.

```python name="agent" listing="1"
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

When the process dies, the stack is gone, and with it everything the function
knew. For a cheap, deterministic function that's fine: run it again. An agent
runs for minutes, burns tokens, gives a different answer every time, and calls
tools that do things in the world.

Say the agent books travel: the model picks a flight, the agent charges the
card, then books the seat. The process dies between the two, we retry, the
model picks a different flight, and the agent charges the card again. The
user paid twice and flew once, and nothing in the code is wrong.

The code is interruption-agnostic: nothing in it acknowledges that failures
exist. The execution is interruption-intolerant: when the process dies, the
progress dies with it. The rest of this post pulls those two apart.

## Memoize every call, keyed by a stable id

The easiest fix is to memoize the function call: store the return value, and
next time, return the stored value instead of calling the function.

Memoization is usually keyed by the arguments, which works for mathematical
functions only. With side effects, the same call with the same arguments can
be two different events: charging the same card the same amount twice is two
charges. So we key by position. The run has an id, its first call is `:1`, its
second `:2`, and a call made from inside `:2` is `:2:1`. The ids are
hierarchical, they sort in the order the execution unfolds, and the same call
gets the same id on every replay.

### The store: create and settle, first writer wins

A function call has an identity, arguments, and either an outcome or nothing
yet. Bundle those together and you have a promise: not the JavaScript kind,
but an in-memory promise with an id, kept in a database instead of a
variable.

```python name="Promise" listing="2"
PENDING, RESOLVED, REJECTED = "pending", "resolved", "rejected"


@dataclass(frozen=True)
class Promise:
    id: str
    state: str = PENDING
    param: Any = None
    value: Any = None
```

A store holds them:

```python name="Store" listing="3"
class Store:
    def __init__(self):
        self._db: dict[str, Promise] = {}

    def create(self, id: str, param: Any) -> Promise:
        return self._db.setdefault(id, Promise(id, param=param))

    def settle(self, id: str, state: str, value: Any) -> Promise:
        p = self._db[id]
        if p.state == PENDING:
            self._db[id] = Promise(id, state, p.param, value)
        return self._db[id]
```

This store is a dict, so the store dies with the process. The interface is
what matters, and the interface is two operations: create a promise, settle a
promise. Over one session:

```python name="Store, in one session" listing="4"
#                                 Promise(id, state, param, value)

s = Store()

s.create("a", 1)                # Promise("a", PENDING, 1)
s.create("a", 2)                # Promise("a", PENDING, 1)      <- 2 discarded

s.settle("a", RESOLVED, 9)      # Promise("a", RESOLVED, 1, 9)
s.settle("a", RESOLVED, 8)      # Promise("a", RESOLVED, 1, 9)  <- 8 discarded
s.settle("a", REJECTED, Err())  # Promise("a", RESOLVED, 1, 9)  <- so is Err

s.create("a", 3)                # Promise("a", RESOLVED, 1, 9)  <- replay sees
```

Nothing after the first `create` changes the param, and nothing after the
first `settle` changes the value. Both operations are first-writer-wins, so
both are idempotent, and that's what makes replay work: a restarted program
calls `create` on an id from a previous life and gets back what happened last
time.

### Wrapping by hand: sixteen lines become sixty-four

With the store in hand, memoizing a function call follows one pattern. Assign
the call a unique id and create the promise. If the promise comes back
pending, call the function, settle the promise, and return the value that
`settle` returns. If the promise comes back settled, return its value. Do that
at every call site in the agent and this is what comes out.

```python name="agent, wrapped by hand" listing="5"
def agent(question, store, run_id):
    messages = [{"role": "user", "content": question}]

    # ---- bookkeeping -------------------------------------------------
    step = 1
    id = f"{run_id}:{step}"

    p = store.create(id, messages)
    if p.state == PENDING:
        try:
            result = prompt(store, id, messages)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == RESOLVED:
        response = p.value
    if p.state == REJECTED:
        raise p.value
    # ------------------------------------------------------------------

    while "tool" in response:
        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}:{step}"

        p = store.create(id, (response["tool"], response["args"]))
        if p.state == PENDING:
            try:
                result = invoke(store, id, response["tool"], response["args"])
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == RESOLVED:
            result = p.value
        if p.state == REJECTED:
            raise p.value
        # --------------------------------------------------------------

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}:{step}"

        p = store.create(id, messages)
        if p.state == PENDING:
            try:
                result = prompt(store, id, messages)
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == RESOLVED:
            response = p.value
        if p.state == REJECTED:
            raise p.value
        # --------------------------------------------------------------

    return response["answer"]
```

A crash shows how this works. Steps `:1` through `:5` are settled in the
store, and `:6` is pending: the tool was mid-flight when the process died.
Restart with the same run id, and `create` returns a settled promise for `:1`
through `:5`, so the code takes each recorded response without calling
anything. At `:6` the promise is pending, so the tool runs, and the loop
carries on.

Create, call, settle, all three in `agent`'s own frame, three times over. The
bookkeeping is interleaved with the business logic: there's no layer to fix,
only call sites.

Note the `p =` on both settle branches. `settle` returns whatever is in the
store after the write, and if another worker beat you to it, that's their
outcome, not yours. So return or raise from what came back, never from your
local result. Drop the assignment and the code still passes tests, and quietly
disagrees with the store exactly when two workers overlap.

Sixteen lines of agent became sixty-four. This is interruption-aware code,
written in terms of the interruptions the program has to survive. That buys
interruption-tolerant execution, and the awareness is the price, charged at
every call site.

The duplication, at least, is easy to fix. Factor it out:

```python name="durable" listing="6"
def durable(store, id, func, *args):
    p = store.create(id, args)
    if p.state == PENDING:
        try:
            result = func(store, id, *args)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == RESOLVED:
        return p.value
    if p.state == REJECTED:
        raise p.value
```

Now every call site is one line:

```python name="call site" listing="7"
response = durable(store, f"{run_id}:{step}", prompt, messages)
```

Better: create, call, and settle now happen in `durable`'s frame, one level
below `agent`. But every call site still has to remember to go through
`durable`, and forget once, that step re-executes on every replay. Three
things aren't gone.

**The store and the id are in the signature.** Every caller of `agent` has to
supply them, and so does everything `agent` calls. That's how durability
composes, and how it leaks, upward through every signature.

**The counter has to be right.** Position has to land on the same number on
every replay. Add an `if` on a timestamp and the counter drifts: the agent
resumes with someone else's answer, and no test catches it. Recovery is only
correct if the code between steps is deterministic, and nothing says so.

**A step can still run twice.** The process can die between the tool
finishing and the settle committing, and nothing can close that window over a
network. What the store can do is give the attempt a stable id, so the tool
passes the id along as an idempotency key and the other side deduplicates.

The third is a property of the problem and doesn't change. The first two do.

### A decorator: the same sixteen lines, and they survive

Nothing in `durable` mentions agents, models, or tools; the shape is the same
for every call in every durable function anyone will write. So make it the
primitive: persist promises, and let the call sites use them.

```python name="agent" listing="8"
@resonate
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

That's the agent from the top of this post, character for character, plus one
line. The bookkeeping didn't move into a helper; the bookkeeping moved under
the language. Every call derives an id, creates the promise, runs if pending,
settles, and reads back. A crash and restart replays the function, finds the
promises that survived, and skips past the work they stand for.

Interruption-agnostic code, interruption-tolerant execution. The guarantee is
the same as before. What changed is where the awareness lives: out of your
program, into the runtime.

`durable` is the runtime's frame, and the frames above it are always the same
three, whatever the call underneath. That's the manual diagram with one frame
slid under every call, including the call to `agent`, whose own promise is
now created and settled by the same code that handles every step.

State 4 is the interesting one on a restart. `durable` derives the same id,
finds `agent.012d7:1` already resolved, and returns the value without ever
reaching state 6. Same at 9 and 14, until the first id the store doesn't know.
Every frame in that picture disappears when the process dies. The column on
the right doesn't.

## Why the primitive is a promise, not a workflow

A call is how a program says: block until this value is known. Nothing about
that requires the value to be produced in this process, or within this
process's lifetime. From there the rest falls out: recovery is reading ids you
already have, fan-out is many ids, a timeout is a promise settled by a clock.

A workflow DSL gets you there too, but you give up your own language: every
branch, loop, and retry is re-expressed in the engine's terms, and your
debugger and type checker stop applying to the part that matters. Here the
control flow stays plain Python, and the durability comes from the store.

## What durable execution asks of your code

The same asks the hand-wrapped version made, now invisible.

**Code between calls must be deterministic.** Read the clock or roll dice
inside a durable call, never in between.

**Side effects must be idempotent at the boundary.** The runtime gives every
attempt a stable id; whether the other end honours it is up to you.

**Recorded values must be serialisable.** Replay reads every one of them back.

**A run is not a process.** A run has an id, can outlive the machine that
started it, and can be picked up by two workers at once. First-writer-wins is
what stops both of them doing step seven. The next post starts there.

## What's left to build: the other five thousand lines

The idea is small, but the engineering isn't:

- **A real store.** `create` and `settle` under concurrent writers, across
  processes and regions, atomically.
- **A scheduler and a queue.** Which pending promises are being worked on,
  and by whom.
- **Leases.** A worker that dies mid-call has to be noticed and its work
  reassigned.
- **At-least-once, handled once.** In one place, instead of at every call
  site.

Every listing in this post runs as written, and the engine gets built up from
them in the [repository](https://github.com/resonatehq/durable-execution).
The next post is about the calls this process doesn't make itself.
