Listing 1 shows a simple tool-calling agent: First the function prompts a model. If the model returns a tool call, the function invokes the tool, and prompts the model again. When the model returns an answer instead of a tool call, the function returns the answer.

```python name="agent" listing="1"
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

The agent works on the happy path but has several problems in case of a failure. The program is ephemeral, if the process crashes the program loses progress. That's okay for a function that runs in ten milliseconds, is free, deterministic, has no or only well-behaved side effects. That's not okay for an agent that runs for minutes, burns tokens, is non-deterministic, and calls a variety of tools.

Imagine an agent that decides to perform a service. The agent charges a user's credit card and then performs the service. If the process crashes after charging the card then we retry the agent call and burn additional tokens, the agent may decide on a different service and charge the credit card again, performing the different service. Not only was this failure costly to us, spending more tokens, the failure was costly to the user, getting charged for two different services receiveing only one.

Nothing in this code acknoledges the possibility of failures. We call this interruption-agnostic code. crashing. Unfortunately, when the process crashes, progress is lost. We call that interruption-intollerant execution. 

# A solution.

Obviously we need a solution for this problem. The easiest solution is to memoize the function call: We simply store the return value of the function. That's it. We just have to ensure the function invocation gets a stable id. We define a durable promise

### The store

A function call has an identity, the arguments the step was called with, and either an outcome or not one yet. That is a promise — not the JavaScript kind; a smaller, stricter thing:. Similar to an emphemeral promise but with an identifier and we store the value in the database

```python name="Promise" listing="3"
PENDING, RESOLVED, REJECTED = "pending", "resolved", "rejected"


@dataclass(frozen=True)
class Promise:
    id: str
    state: str = PENDING
    param: Any = None
    value: Any = None
```

And a store holds them:

```python name="Store" listing="4"
class Store:
    def __init__(self):
        self._db: dict[str, Promise] = {}

    def create(self, id: str, param: Any) -> Promise:
        return self._db.setdefault(id, Promise(id, param=param))

    def settle(self, id: str, state: str, value: Any) -> Promise:
        p = self._db[id]
        if p.state == PENDING:
            self._db[id] = Promise(id, state, p.param, value)
        return self._db[id]
```

This store is a dict, so the store dies with the process. Useless for the actual job, but what matters is the interface:
two operations, to create a promise and to settle a promise. Create and settle are idempotent.


```python name="Store, in one session" listing="5"
#                                 Promise(id, state, param, value)

s = Store()

s.create("a", 1)                # Promise("a", PENDING, 1)
s.create("a", 2)                # Promise("a", PENDING, 1)      <- 2 discarded

s.settle("a", RESOLVED, 9)      # Promise("a", RESOLVED, 1, 9)
s.settle("a", RESOLVED, 8)      # Promise("a", RESOLVED, 1, 9)  <- 8 discarded
s.settle("a", REJECTED, Err())  # Promise("a", RESOLVED, 1, 9)  <- so is Err

s.create("a", 3)                # Promise("a", RESOLVED, 1, 9)  <- replay sees
```

Nothing after the first create changes the param, and nothing after the first
settle changes the value.

**`create` is idempotent.** Idempotence is what makes replay work: a
restarted program calls `create` on ids that already exist and gets back what
happened last time.

**Settling is first-writer-wins.** `settle` moves a pending promise to
`RESOLVED` or `REJECTED`, and refuses to move a settled one anywhere. A step
that runs twice cannot produce two different outcomes of record.

**Settling returns the promise, and it is not necessarily yours.** This is the
one that is easy to skip. `settle` returns whatever is in the store *after* the
write — which, if someone beat you to it, is their outcome and not the one you
just passed in. So the rule at every call site is: settle, then read what came
back, then return or raise from that. Never from your local result.

Skipping the read-back looks harmless until two workers run the same step.
Worker A calls the model and gets a response. Worker B calls the model and the
request times out. Both settle the promise; the store keeps whichever landed
first, say A's value. If B raises its own timeout instead of reading back, the
two workers now disagree about what that step did, and carry that disagreement
forward into two different message histories for the same run.

The same rule covers restarts, not just races. On replay the promise may already
be rejected from the first run. You raise the stored error. You do not call the
model again to find out.

### A first solution, wrapping by hand

Now put the store in the agent. Every call site gets the same treatment: build
an id, create the promise, do the work if it is still pending, settle it either
way, then return or raise based on what the store says.

```python name="agent, wrapped by hand" listing="7"
def agent(question, store, run_id):
    messages = [{"role": "user", "content": question}]

    # ---- bookkeeping -------------------------------------------------
    step = 1
    id = f"{run_id}.{step}"

    p = store.create(id, messages)
    if p.state == PENDING:
        try:
            result = prompt(store, id, messages)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == REJECTED:
        raise p.value
    response = p.value
    # ------------------------------------------------------------------

    while "tool" in response:
        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}.{step}"

        p = store.create(id, (response["tool"], response["args"]))
        if p.state == PENDING:
            try:
                result = invoke(store, id, response["tool"], response["args"])
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == REJECTED:
            raise p.value
        result = p.value
        # --------------------------------------------------------------

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}.{step}"

        p = store.create(id, messages)
        if p.state == PENDING:
            try:
                result = prompt(store, id, messages)
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == REJECTED:
            raise p.value
        response = p.value
        # --------------------------------------------------------------

    return response["answer"]
```

This works, and a crash shows how. Call the run `agent.012d7`. Steps `agent.012d7:1` through
`agent.012d7:5` are settled in the store; `agent.012d7:6` is pending — the tool was mid-flight
when the process died. Restart with the same run id. `create("agent.012d7", ...)`
returns the settled promise, so the code skips the pending block and takes the
recorded response. Same for two through five. At `agent.012d7:6` the promise is
pending, so the tool runs, settles, and the loop carries on. Five steps
replayed from the store in milliseconds, one step resumed, the rest executed
fresh.

Most teams end up here, and the code is correct as written. Nothing is wrong
with the approach except the cost.

Three things happen, in that order, and all three happen in `agent`'s own
frame. The bookkeeping is not underneath the business logic but interleaved
with it. That is not a metaphor for the maintenance problem. That is the
maintenance problem: there is no layer to fix, only call sites.

Note the `p =` on both settle branches. That assignment is the whole third
property. Write `store.settle(id, RESOLVED, value)` without the assignment and
the code still runs, still passes tests, and quietly returns local outcomes
the store disagrees with. The failure comes only when two workers overlap,
which is exactly the case the store exists for.

The obvious cost is that sixteen lines of agent became sixty-one. Everything
between the rules is bookkeeping; what is left outside them is the program you
meant to write — eight lines of it, with its three calls swallowed by the
blocks. Three call sites, three copies of the same block.

This is interruption-aware code: the program is now written in terms of the
interruptions the program has to survive. The trade does buy
interruption-tolerant execution, which is what you wanted. The awareness is
the price, and the price is charged at every call site.

The duplication part is easy to fix — factor it out:

```python name="durable" listing="8"
def durable(store, id, func, *args):
    p = store.create(id, args)
    if p.state == PENDING:
        try:
            result = func(store, id, *args)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == REJECTED:
        raise p.value
    return p.value
```

Which turns every call site into one line:

```python name="call site" listing="9"
response = durable(store, f"{run_id}.{step}", prompt, messages)
```

Good. The duplication is gone, and the read-back is now written once instead
of at every call site. The helper also changes the picture above: create,
call, and settle now happen in `durable`'s frame, one level below `agent`.
Hold on to that; that is where this is going. But every call site still has to
remember to go through `durable` rather than calling the function directly,
and forgetting once means that step silently re-executes on every replay. The
awareness has been compressed, not removed.

Three things are not gone.

**The store and the id are part of the signature.** `agent` needs a `store`
and a `run_id` to be durable, so every caller needs them — and so does
everything `agent` calls, which is why `prompt` and `invoke` now take them too,
and why they must pass them on again to anything they call. The id handed down
is the parent of the ids that come back: step `run1.2` creates `run1.2.1`
beneath. That is how durability composes, and also how durability leaks:
upward through the type of every function that participates.

**The id is a counter, and the counter has to be right.** In a straight line
of code you can name your steps `"plan"`, `"search"`, `"report"`. In a loop
there is no fixed set of steps, so identity falls back on position — and
position has to land on the same number for the same call on every replay.
That means the replayed program has to take the same path through the loop.
Recovery is only correct if the function is deterministic between recorded
steps, and nothing in the code says so. Add an `if` on a timestamp, iterate a
set, skip a tool call when a flag is set, and the counter drifts. Step 7 on
the replay is not step 7 from the first run, and the agent resumes with
someone else's answer. No test catches this; the symptom is an agent that
occasionally continues a conversation the agent never had. Determinism is not
a nice-to-have here. Determinism is the thing addressing is built on.

**A step can still run twice.** Between the tool finishing and the settle
committing, the process can die. The call happened, the record did not, and on
restart you make the call again. You can shrink that window but you cannot
close the window — nothing can, over a network. What the store can do is give
the attempt a stable identity. The id already travels downstream, so the tool
passes the id along as an idempotency key, and the email service or the
payment processor deduplicates on their side. Exactly-once is not a property
you get. Exactly-once is a property you assemble, from at-least-once execution
plus deduplication at every boundary that matters. First-writer-wins plus
reading back is what keeps the at-least-once half from turning into
disagreement.

The third one is a property of the problem, not of this approach — it does not
change in the next section. The first two do.

## Interruption-agnostic code

Look at what `durable` actually does: takes an identity, checks whether an
outcome is known, produces one if not, records the outcome, and reports
whatever the store ended up holding. Nothing in the helper mentions agents,
models, or tools. No version of the helper would be specific to this program —
the shape is the same for every call in every durable function anyone will
ever write.

The best solution is to stop threading that by hand and make it the primitive.
Persist promises, and let the call sites use them.

```python name="agent" listing="10"
@resonate
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

That is the agent from the top of this post, character for character, plus one
line. The bookkeeping did not move into a helper; the bookkeeping moved under
the language. `prompt(messages)` derives an id, creates the promise, runs
the call if the promise is pending, settles the promise, reads back what the
store holds, and returns or raises from that. A crash and restart replays the
function, finds the promises that survived, and skips past the work they
represent.

Interruption-agnostic code, interruption-tolerant execution. Nothing about the
guarantee changed between this section and the last one. What changed is where
the awareness lives: out of your program, into the runtime. The two properties
that started out fused have been separated, and the seam is the function call.
Fourteen lines at the top of this post; fourteen lines here. The difference is
that these fourteen do not die.

The call site no longer calls `prompt` but `durable`, and `durable` is the
runtime's frame — deriving the id, creating the promise, calling the real
function, and settling the promise with whatever came back. The frames above
`durable` are always these three, in this order, whatever the call underneath
happens to be. From where the agent stands, `prompt(messages)` returned a
response, same as always. That is the manual diagram with one frame slid
underneath, the same frame the `durable` helper pushed, except you no longer
pass a store or an id and no longer have to remember to call the thing at all.

Step 2 is the interesting one on a restart. `durable` derives the same id, finds
the promise already settled from a previous life of this program, and returns
its value without ever reaching step 5. The model is not called again.

Every frame in that picture disappears when the process dies. The promise
created in step 3 does not. That is the entire trick: the stack is ephemeral, so
put the record somewhere the stack is not.

The store is gone from the signature — the decorator supplies the store. The
counter is gone too. The counter still exists, maintained by code whose only
job is maintaining it, so the same id is computed on every replay rather than
depending on you not having written an `if` in the wrong place. And the `p =`
you have to remember thirty times is written once, in the runtime, where
forgetting is a bug someone else already found.

## Why promises

A promise is the right primitive because it is already the unit that both the
language and the network agree on.

The language agrees: a call is how a program says *block until this value is
known*. Nothing about that requires the value to be produced in this process,
or within this process's lifetime. Point a call at a persisted promise and the
same syntax means block until this value is known, wherever and whenever the
value becomes known. `raise` comes along for free — a rejected promise is an
exception that survived a restart.

The network agrees: a remote call is a promise held by someone else. The
caller does not need to know which process settles the promise, or whether
that process is the one that started the work. The caller waits on an id.

From there the rest falls out. Recovery is reading ids you already have. Fan-out
is many ids. A timeout is a promise settled by a clock instead of a function. A
retry is a policy on an unsettled promise. Concurrency across machines is a
promise whose children are also promises.

None of that needs a workflow DSL, a state machine, or a YAML file describing
your control flow. The control flow is the Python. The durability is the store.

## What you are signing up for

None of this is free, and the asks are worth stating plainly, because they are
the same asks the hand-wrapped version made — they have only stopped being
visible.

**Your code between calls must be deterministic.** Replay re-runs that code,
and the re-run has to arrive at the same calls in the same order. Read the
clock or roll dice inside an awaited call, where the result gets recorded;
never in between.

**Your side effects must be idempotent at the boundary.** The runtime can give
every attempt a stable id. Whether the thing on the other end honours the id
is up to you.

**Your recorded values must be serialisable, and reasonably sized.** They are
going into a store, and replay means reading every one of them back.

**A run is a different kind of object than a process.** A run has an id. A run
can outlive the machine that started the run and finish on another. Two
workers can pick up the same run, and first-writer-wins is what stops both of
them doing step seven: the loser gets the winner's promise back and moves on.
Hold on to that one — the next post is built on top of that.
