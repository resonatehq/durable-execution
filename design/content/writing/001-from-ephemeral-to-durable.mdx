Listing 1 shows a simple tool-calling agent. First the function prompts a
model. If the model returns a tool call, the function invokes the tool and
prompts the model again. When the model returns an answer instead of a tool
call, the function returns the answer.

```python name="agent" listing="1"
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

The agent works on the happy path, but a failure exposes several problems. The
program is ephemeral: if the process crashes, the program loses all its
progress. That's fine for a function that runs in ten milliseconds, is free,
is deterministic, and has no side effects or only well-behaved ones. That's
not fine for an agent that runs for minutes, burns tokens, is
non-deterministic, and calls a variety of tools.

Say the agent books travel. The model picks a flight, the agent charges the
user's card, then books the flight. Now the process crashes between the charge
and the booking. We retry. The model is non-deterministic, so on the second
run it may well pick a different flight — and the agent charges the card again
and books that one. The user got charged twice and flew once. We paid twice
for the tokens. And nothing in the code is wrong; the crash just landed
between two steps that were supposed to go together.

Nothing in this code acknowledges that failures exist. We call that
interruption-agnostic code. And when the process crashes, progress is gone. We
call that interruption-intolerant execution.

## A solution

The easiest solution is to memoize the function call: store the return value,
and next time, don't call the function — return the stored value. That's it.
The only thing we have to add is a stable id for each invocation, so we can
find the stored value again.

### The store

A function call has an identity, the arguments the call was made with, and
either an outcome or nothing yet. Bundle those together and you have a
promise. Not the JavaScript kind — a smaller, stricter thing: an in-memory
promise plus an id, stored in a database instead of a variable.

```python name="Promise" listing="2"
PENDING, RESOLVED, REJECTED = "pending", "resolved", "rejected"


@dataclass(frozen=True)
class Promise:
    id: str
    state: str = PENDING
    param: Any = None
    value: Any = None
```

And a store holds them:

```python name="Store" listing="3"
class Store:
    def __init__(self):
        self._db: dict[str, Promise] = {}

    def create(self, id: str, param: Any) -> Promise:
        return self._db.setdefault(id, Promise(id, param=param))

    def settle(self, id: str, state: str, value: Any) -> Promise:
        p = self._db[id]
        if p.state == PENDING:
            self._db[id] = Promise(id, state, p.param, value)
        return self._db[id]
```

This store is a dict, so the store dies with the process. Useless for the real
job, but the interface is what matters, and the interface is two operations:
create a promise, settle a promise. Both are first-writer-wins, and that makes
both idempotent: the first call sets the record, and every later call returns
that record no matter what arguments come with it. Here's what that means in
practice:


```python name="Store, in one session" listing="4"
#                                 Promise(id, state, param, value)

s = Store()

s.create("a", 1)                # Promise("a", PENDING, 1)
s.create("a", 2)                # Promise("a", PENDING, 1)      <- 2 discarded

s.settle("a", RESOLVED, 9)      # Promise("a", RESOLVED, 1, 9)
s.settle("a", RESOLVED, 8)      # Promise("a", RESOLVED, 1, 9)  <- 8 discarded
s.settle("a", REJECTED, Err())  # Promise("a", RESOLVED, 1, 9)  <- so is Err

s.create("a", 3)                # Promise("a", RESOLVED, 1, 9)  <- replay sees
```

Nothing after the first create changes the param. Nothing after the first
settle changes the value.

**Both are first-writer-wins.** The first `create` fixes the param. The first
`settle` fixes the outcome. A later call with the same id changes nothing,
whatever arguments come with it — so a step that runs twice can't end up with
two different outcomes on record.

**And so both are idempotent.** Call either one again and you get back exactly
what the first call produced. That's what makes replay work: a restarted
program calls `create` on ids that already exist and gets back what happened
last time, and a retried `settle` can't overwrite an answer that's already
there.


### A first solution, wrapping by hand

Now put the store in the agent. Every call site gets the same treatment: build
an id, create the promise, do the work if the promise is still pending, settle
either way, then return or raise based on what the store says.

```python name="agent, wrapped by hand" listing="5"
def agent(question, store, run_id):
    messages = [{"role": "user", "content": question}]

    # ---- bookkeeping -------------------------------------------------
    step = 1
    id = f"{run_id}:{step}"

    p = store.create(id, messages)
    if p.state == PENDING:
        try:
            result = prompt(store, id, messages)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == RESOLVED:
        response = p.value
    if p.state == REJECTED:
        raise p.value
    # ------------------------------------------------------------------

    while "tool" in response:
        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}:{step}"

        p = store.create(id, (response["tool"], response["args"]))
        if p.state == PENDING:
            try:
                result = invoke(store, id, response["tool"], response["args"])
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == RESOLVED:
            result = p.value
        if p.state == REJECTED:
            raise p.value
        # --------------------------------------------------------------

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        # ---- bookkeeping ---------------------------------------------
        step += 1
        id = f"{run_id}:{step}"

        p = store.create(id, messages)
        if p.state == PENDING:
            try:
                result = prompt(store, id, messages)
                p = store.settle(id, RESOLVED, result)
            except Exception as e:
                p = store.settle(id, REJECTED, e)

        if p.state == RESOLVED:
            response = p.value
        if p.state == REJECTED:
            raise p.value
        # --------------------------------------------------------------

    return response["answer"]
```

This works, and a crash shows how. Call the run `agent.012d7`. Steps
`agent.012d7:1` through `:5` are settled in the store; `:6` is pending — the
tool was mid-flight when the process died. Restart with the same run id.
`create("agent.012d7:1", ...)` returns the settled promise, so the code skips
the pending block and takes the recorded response. Same for two through five.
At `:6` the promise is pending, so the tool runs, settles, and the loop
carries on. Five steps replayed from the store in milliseconds, one step
resumed, the rest run fresh.

Most teams end up here, and the code is correct. There's nothing wrong with
this approach except the cost.

Three things happen, in that order, and all three happen in `agent`'s own
frame. The bookkeeping isn't underneath the business logic; it's interleaved
with it. That's not a metaphor for the maintenance problem. That is the
maintenance problem: there's no layer to fix, only call sites.

Note the `p =` on both settle branches. `settle` returns whatever is in the
store *after* the write — and if someone beat you to it, that's their outcome,
not the one you just passed in. So the rule at every call site is: settle,
then read what came back, then return or raise from that. Never from your
local result. Drop the assignment and write `store.settle(id, RESOLVED,
value)` on its own, and the code still runs, still passes tests, and quietly
returns local outcomes the store disagrees with. The failure only shows up
when two workers overlap — which is exactly the case the store exists for.

That looks harmless until two workers run the same step. Worker A calls the
model and gets a response. Worker B calls the model and times out. Both settle
the promise; the store keeps whichever landed first, say A's. If B raises its
own timeout instead of reading back, the two workers now disagree about what
that step did, and they carry that disagreement forward into two different
message histories for the same run.

The same rule covers restarts, not just races. On replay the promise may
already be rejected from the first run. You raise the stored error. You don't
call the model again to find out.

The obvious cost: sixteen lines of agent became sixty-four. Everything between
the rules is bookkeeping. What's left outside them is the program we meant to
write — eight lines, with its three calls swallowed by the blocks. Three call
sites, three copies of the same block.

This is interruption-aware code: the program is now written in terms of the
interruptions it has to survive. And that does buy interruption-tolerant
execution, which is what we wanted. The awareness is the price, and the price
is charged at every call site.

The duplication is easy to fix — factor it out:

```python name="durable" listing="6"
def durable(store, id, func, *args):
    p = store.create(id, args)
    if p.state == PENDING:
        try:
            result = func(store, id, *args)
            p = store.settle(id, RESOLVED, result)
        except Exception as e:
            p = store.settle(id, REJECTED, e)

    if p.state == RESOLVED:
        return p.value
    if p.state == REJECTED:
        raise p.value
```

Which turns every call site into one line:

```python name="call site" listing="7"
response = durable(store, f"{run_id}:{step}", prompt, messages)
```

Good. The duplication is gone, and the read-back is written once instead of at
every call site. The helper also changes the picture above: create, call, and
settle now happen in `durable`'s frame, one level below `agent`. Hold on to
that; that's where this is going. But every call site still has to remember to
go through `durable` rather than calling the function directly, and forget
once and that step silently re-executes on every replay. The awareness has
been compressed, not removed.

Three things aren't gone.

**The store and the id are in the signature.** `agent` needs a `store` and a
`run_id` to be durable, so every caller needs them — and so does everything
`agent` calls, which is why `prompt` and `invoke` take them now, and why they
have to pass them on to anything they call. The id handed down is the parent
of the ids that come back: step `agent.012d7:2` creates `agent.012d7:2:1`
beneath. That's how durability composes, and also how it leaks: upward,
through the type of every function that takes part.

**The id is a counter, and the counter has to be right.** In straight-line
code you can name your steps `"plan"`, `"search"`, `"report"`. In a loop
there's no fixed set of steps, so identity falls back on position — and
position has to land on the same number for the same call on every replay.
That means the replayed program has to take the same path through the loop.
Recovery is only correct if the function is deterministic between recorded
steps, and nothing in the code says so. Add an `if` on a timestamp, iterate a
set, skip a tool call when a flag is set, and the counter drifts. Step 7 on
the replay isn't step 7 from the first run, and the agent resumes with someone
else's answer. No test catches this. The symptom is an agent that occasionally
continues a conversation it never had. Determinism isn't a nice-to-have here.
Determinism is what addressing is built on.

**A step can still run twice.** Between the tool finishing and the settle
committing, the process can die. The call happened, the record didn't, and on
restart we make the call again. We can shrink that window but we can't close
it — nothing can, over a network. What the store can do is give the attempt a
stable identity. The id already travels downstream, so the tool passes it
along as an idempotency key, and the payment processor deduplicates on their
side. Exactly-once isn't a property you get. Exactly-once is a property you
assemble: at-least-once execution plus deduplication at every boundary that
matters. First-writer-wins plus reading back is what keeps the at-least-once
half from turning into disagreement.

The third one is a property of the problem, not of this approach, and it
doesn't change in the next section. The first two do.

### A second solution, a decorator

Look at what `durable` actually does: takes an identity, checks whether an
outcome is known, produces one if not, records it, and reports whatever the
store ended up holding. Nothing in the helper mentions agents, models, or
tools. No version of the helper would be specific to this program — the shape
is the same for every call in every durable function anyone will ever write.

So stop threading that by hand. Make it the primitive: persist promises, and
let the call sites use them.

```python name="agent" listing="8"
@resonate
def agent(question):
    messages = [{"role": "user", "content": question}]

    response = prompt(messages)

    while "tool" in response:
        result = invoke(response["tool"], response["args"])

        messages += [
            {"role": "assistant", "content": response},
            {"role": "tool", "content": result},
        ]

        response = prompt(messages)

    return response["answer"]
```

That's the agent from the top of this post, character for character, plus one
line. The bookkeeping didn't move into a helper; the bookkeeping moved under
the language. `prompt(messages)` derives an id, creates the promise, runs the
call if the promise is pending, settles the promise, reads back what the store
holds, and returns or raises from that. A crash and restart replays the
function, finds the promises that survived, and skips past the work they stand
for.

Interruption-agnostic code, interruption-tolerant execution. Nothing about the
guarantee changed between this section and the last. What changed is where the
awareness lives: out of your program, into the runtime. The two properties
that started out fused have been pulled apart, and the seam is the function
call. Sixteen lines at the top of this post; sixteen lines here. The
difference is that these sixteen don't die.

The call site no longer calls `prompt` but `durable`, and `durable` is the
runtime's frame — it derives the id, creates the promise, calls the real
function, and settles the promise with whatever came back. The frames above
`durable` are always these three, in this order, whatever the call underneath
happens to be. From where the agent stands, `prompt(messages)` returned a
response, same as always. That's the manual diagram with one frame slid
underneath every call — including the call to `agent`. The decorator is that
bottom frame: the run gets a promise of its own, `agent.012d7`, pending from
state 2 until `agent` returns at state 19. By hand, nothing recorded the run;
now the run is just another durable call, and the steps hang off its id.

State 4 is the interesting one on a restart. `durable` derives the same id,
finds `agent.012d7:1` already resolved from a previous life of this program,
and returns the value without ever reaching state 6. The model isn't called
again. Same at 9 and 14, until the first id the store doesn't know.

Every frame in that picture disappears when the process dies. The column on
the right doesn't. That's the entire trick: the stack is ephemeral, so put the
record somewhere the stack isn't.

The store is gone from the signature — the decorator supplies the store. The
counter is gone too. Well, the counter still exists, but it's maintained by
code whose only job is maintaining it, so the same id comes out on every
replay rather than depending on you not having written an `if` in the wrong
place. And the `p =` you'd have to remember thirty times is written once, in
the runtime, where forgetting is a bug someone else already found.

## Why promises

A promise is the right primitive because it's already the unit that both the
language and the network agree on.

The language agrees: a call is how a program says *block until this value is
known*. Nothing about that requires the value to be produced in this process,
or within this process's lifetime. Point a call at a persisted promise and the
same syntax means block until this value is known, wherever and whenever that
happens. `raise` comes along for free — a rejected promise is an exception
that survived a restart.

The network agrees: a remote call is a promise held by someone else. The
caller doesn't need to know which process settles the promise, or whether that
process is the one that started the work. The caller waits on an id.

From there the rest falls out. Recovery is reading ids you already have. Fan-out
is many ids. A timeout is a promise settled by a clock instead of a function. A
retry is a policy on an unsettled promise. Concurrency across machines is a
promise whose children are also promises.

None of that needs a workflow DSL, a state machine, or a YAML file describing
your control flow. The control flow is the Python. The durability is the
store.

## What you are signing up for

None of this is free, and the asks are worth stating plainly, because they're
the same asks the hand-wrapped version made — they've just stopped being
visible.

**Your code between calls must be deterministic.** Replay re-runs that code,
and the re-run has to arrive at the same calls in the same order. Read the
clock or roll dice inside a durable call, where the result gets recorded —
never in between.

**Your side effects must be idempotent at the boundary.** The runtime can give
every attempt a stable id. Whether the thing on the other end honours the id
is up to you.

**Your recorded values must be serialisable, and reasonably sized.** They're
going into a store, and replay means reading every one of them back.

**A run is a different kind of object than a process.** A run has an id. A run
can outlive the machine that started it and finish on another. Two workers can
pick up the same run, and first-writer-wins is what stops both of them doing
step seven: the loser gets the winner's promise back and moves on. Hold on to
that one — the next post is built on top of it.

## What that leaves

The idea is small. The engineering isn't, and that's where the rest of this
project goes:

- **A real store.** `create` and `settle` have to keep their properties under
  concurrent writers, across processes, across regions — which a dict doesn't.
  In particular, settle-and-return-the-winner has to be one atomic operation,
  not a read followed by a write.
- **The scheduler and the queue.** Something has to decide which pending
  promises are being worked on, and by whom.
- **Leases and failure detection.** A worker that dies mid-call has to be
  noticed and its work reassigned, without two workers running the same step
  in parallel more often than necessary.
- **At-least-once, and living with it.** The window is still there. It gets
  handled once, in one place, instead of at every call site.

That's roughly five thousand lines. The next post is about the calls this
process doesn't make itself.
